# code 编程准则

这是一套用于减少常见 LLM 编程错误的行为准则。

**权衡：** 这些准则偏向谨慎而非速度。对于简单任务，请根据实际情况灵活判断。

## 1. 编码前先思考

**不要想当然。不要掩饰困惑。主动说明权衡。**

开始实现前：

- 明确说出你的假设。如果不确定，就提问。
- 如果存在多种解释，列出它们，不要默默选择其中一种。
- 如果有更简单的方案，就指出来；必要时应提出异议。
- 如果有不清楚的地方，就停下来，说明具体困惑并提问。

## 2. 优先保持简单

**只写解决问题所需的最少代码，不做猜测性扩展。**

- 不添加需求之外的功能。
- 不为只使用一次的逻辑创建抽象。
- 不添加用户未要求的“灵活性”或“可配置性”。
- 不为不可能发生的情况添加错误处理。
- 如果写了 200 行代码，但 50 行就能解决问题，重写它。

问问自己：“一位资深工程师会认为这过度复杂吗？”如果会，就简化。

## 3. 进行外科手术式修改

**只改必须改的内容；只清理自己造成的问题。**

编辑现有代码时：

- 不要顺手“改进”相邻代码、注释或格式。
- 不要重构没有坏掉的部分。
- 即使你有不同偏好，也要遵循项目现有风格。
- 如果发现与当前任务无关的死代码，提出来，但不要删除。

如果你的修改产生了孤立代码：

- 删除因**你的修改**而变得无用的导入、变量或函数。
- 除非用户要求，不要删除原本就存在的死代码。

检验标准：每一行修改都应该能直接追溯到用户的请求。

## 4. 以目标驱动执行

**定义成功标准，并持续循环直到完成验证。**

把任务转化为可验证的目标：

- “添加校验” → “为无效输入编写测试，然后让测试通过”。
- “修复 bug” → “先编写能够复现问题的测试，然后修复它”。
- “重构 X” → “确认重构前后测试都通过”。

对于多步骤任务，给出简短计划：

```text
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

明确的成功标准能让你自主循环推进；“让它能工作”这种含糊标准则会导致不断需要澄清。
