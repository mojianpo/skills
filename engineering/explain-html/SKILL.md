# 复杂内容讲解与独立 HTML 可视化

你的目标不是把内容说得更长，而是让目标读者真正抓住：它是什么、为什么重要、怎么运作、下一步该做什么。

默认交付一个独立的 `html` 文件，让用户无需安装依赖、无需启动项目，保存后即可在浏览器中打开查看。用户明确只要文字时，只输出文字，不强行生成页面。

## 一、先判断任务

先识别三个要素：

1. **对象**：要解释什么，来源是文字、代码、数据、错误信息、流程还是图片。
2. **受众**：面向儿童、初学者、业务人员、设计师、工程师、管理者，还是用户指定的某个人。
3. **目的**：是建立直觉、辅助决策、排查问题、学习实现，还是展示数据。

如果受众没有说明，使用“没有技术背景但愿意理解的成年人”作为默认受众，而不是机械地按五岁儿童解释。若受众、准确性或输出形式会显著改变结果，提出一个最小必要的问题；否则基于上下文继续推进。

## 二、解释方法：从直觉到细节

按照读者需要决定深度，但优先遵循以下顺序：

1. **一句话结论**：先说清楚它是什么，以及解决什么问题。
2. **熟悉的类比**：用读者已有经验建立直觉。类比必须说明边界，不能让类比替代事实。
3. **最小模型**：只保留理解主题所需的 3～7 个关键概念或步骤。
4. **因果链**：明确“输入 → 发生什么 → 输出”，不要只罗列定义。
5. **具体例子**：使用一组小而真实的例子，展示变化前后或完整过程。
6. **边界与代价**：说明什么时候不适用、常见误解、主要取舍和风险。
7. **行动建议**：以读者能执行的下一步收尾。

语言要求：

- 一句话只承担一个主要意思；先用日常语言，再在必要处给出术语。
- 每个不可避免的术语首次出现时立即解释，不堆缩写。
- 先讲“为什么”和“做什么”，再讲语法、API 或实现细节。
- 不以“这很简单”“显然”等话评价读者；简单是表达方式，不是降低内容质量。
- 技术读者需要机制、约束和取舍；业务读者需要影响、成本、风险和决策；初学者需要具体步骤和可观察结果。

## 三、独立 HTML 的交付标准

### 页面结构

页面应围绕一个明确问题组织，通常包含：

- 标题与一句话结论；
- “先看懂”区域：类比、核心模型或关键数字；
- “怎么运作”区域：流程、时间线、关系图、分步卡片或可展开细节；
- “举个例子”区域：输入、过程、输出的对应关系；
- “注意边界”区域：误区、限制、取舍或排错提示；
- 页面底部的来源、假设或更新时间（如果有）。

不必把所有内容都做成卡片。根据主题选择最能降低理解成本的视觉形式：

| 内容关系 | 优先形式 |
| --- | --- |
| 顺序和因果 | 流程图、时间线、步骤动画 |
| 数量和比例 | 条形图、对比条、简单图表 |
| 层级和组成 | 分层结构图、嵌套模块 |
| 多个方案 | 对比表、决策树 |
| 代码行为 | 代码片段 + 行号标注 + 执行流程 |
| 错误排查 | 症状 → 原因 → 检查 → 修复路径 |

### 技术约束

- 必须是一个完整 HTML 文件：包含 `<!doctype html>`、`<head>` 和 `<body>`，内联 CSS 与 JavaScript。
- 默认不依赖构建工具、框架、CDN、网络字体或外部图片；内容应在离线状态下仍能阅读和交互。
- 优先使用语义化 HTML、CSS 和原生 JavaScript。只有在用户明确要求或数据规模确有必要时才引入库，并说明依赖。
- 可视化应服务于解释，不为“看起来丰富”添加无意义动画、粒子、3D 或装饰。
- 数据、单位、计算方式和示例假设必须可追溯；不确定的内容明确标注，不编造精确数字。
- 代码类主题要展示关键代码，而不是只做抽象图；代码必须与解释中的行为一致。

### 交互与状态

只有当交互能帮助用户比较、探索或按步骤理解时才添加交互。交互控件需要有明确反馈，并考虑以下状态：

- **Loading**：初始化或计算期间显示正在处理的状态；
- **Empty**：没有数据或尚未选择内容时说明原因和下一步；
- **Error**：输入无效或计算失败时给出可理解的错误和恢复方式；
- **Disabled**：条件不足时禁用控件，并说明需要什么条件。

如果页面没有动态交互，不要伪造这些状态。按钮、标签页、折叠区和图表说明应支持键盘操作，并有可见的焦点状态。

### 响应式与可访问性

- 先保证手机窄屏可读，再增强桌面布局；避免固定宽度导致横向滚动。
- 文本、图例和图表不要只依赖颜色表达；提供标签、数值或文字说明。
- 使用足够的对比度、可读字号和合理行高；动画支持 `prefers-reduced-motion`。
- 为图表和流程图提供简短的文本摘要；装饰性 SVG 使用适当的无障碍属性。
- 页面标题、标题层级、按钮名称和表单标签要完整。

## 四、实现流程

1. **理解材料**：阅读相关代码、数据或原文，先写出不超过三句的事实摘要。不要在未理解来源时直接美化页面。
2. **提炼模型**：确定一句话结论、关键概念、因果链、一个例子和边界条件。
3. **选择视觉表达**：只选择最能呈现核心关系的 1～2 种图形；先安排信息层级，再写样式。
4. **实现单文件页面**：沿用用户提供的颜色、品牌或设计 Token；没有现成 Token 时使用克制、可读的中性方案。
5. **加入必要交互**：每个交互都回答“它让用户更容易理解什么”，并实现相关状态和恢复路径。
6. **自检和交付**：检查离线打开、窄屏布局、文字准确性、控制台错误、键盘操作和图表文字替代说明。交付文件路径，并简要说明打开方式和已知假设。

## 五、不同主题的重点

- **概念**：先建立心智模型，再补正式定义；避免把百科条目堆在一起。
- **代码**：先解释用途和数据流，再解释关键行；指出输入、状态、副作用和失败路径。
- **错误**：区分现象、直接原因、根因和修复验证方式；不要只翻译错误文本。
- **流程**：标出参与者、触发条件、状态变化和决策分支；用时间顺序或因果关系组织。
- **数据**：先说结论和口径，再展示图表；说明样本、时间范围、单位和可能误导之处。
- **方案比较**：明确比较维度、适用场景和取舍，不把主观偏好伪装成事实。

## 六、完成前检查

在声称完成前，确认：

- 页面是否能脱离项目直接打开；
- 首屏是否在几秒内回答“这是什么、为什么要看”；
- 视觉元素是否真的降低了理解成本；
- 复杂术语、数字、来源和假设是否清楚；
- 手机、桌面、键盘和减少动画设置下是否仍可用；
- 所有交互是否有成功、空、加载、错误或禁用时的合理反馈；
- 是否存在无法验证的内容，并已明确告诉用户。

## 输出形式

默认输出：生成或修改独立 HTML 文件，并用简短文字说明页面解决的问题、主要交互和打开方式。除非用户要求，不输出大段重复的 HTML 源码。

若用户只要求解释：输出结构清晰的中文说明，可保留“结论 → 类比 → 机制 → 例子 → 边界 → 下一步”的顺序；不需要为了形式生成页面。
