# 标书审核

## 目标与边界

对用户指定的招标文件、技术标、商务标和审核规则进行证据驱动的审核。招标文件是合规检查的唯一项目规则来源；通用经验只能作为“提示”，不能据此判定不合规。不得虚构已读取的文件、页码、签章、到账、密封、评分或审核结论。

本技能负责编排以下子技能：

1. `bes-document-parsing`：解析每个招标/投标文件并持久化 Markdown；
2. `bes-bid-rule`：提取业务审核规则；
3. `bes-bid-rule-review`：逐条执行业务规则审核；
4. `bes-bid-compliance-check`：逐条核对招标要求与投标证据；
5. `bes-bid-report`：汇总审核结果并生成 Markdown/HTML 报告。

不要在本技能中重复实现上述子技能的解析、规则抽取或判定逻辑。

## 输入门禁

开始前盘点用户提供的文件和文字，并确认：

- 招标文件：至少一个可读取文件或目录；
- 投标文件：技术标和商务标，或用户明确说明其中一类不适用；
- 项目名称：从用户输入、招标文件或文件名确认；无法确认时暂停并询问；
- 审核规则：用户指定的规则内容/文件，或 `bes-bid-rule` 的默认规则来源。

缺少招标文件或投标文件时，只报告缺口，不启动后续审核。文件存在但不可读、为空、格式不支持或解析失败时，记录为输入错误/部分失败，不得当作“未发现问题”。多份文件要求冲突时，按补遗/澄清优先、日期较新优先、专用条款优先；仍不能解决时标记“待确认”，不得静默裁决。

## 输出路径与安全约束

先根据本文件所在位置确定 `{SKILL_DIR}`，不得把调用者当前工作目录当作技能目录，也不得硬编码绝对路径。所有生成物默认写入：

```text
{SKILL_DIR}/download/{项目名}/
├─ rules/                 业务审核规则及其提取结果
├─ parsing/               招标文件、技术标、商务标解析结果
├─ results/check/         业务规则逐条审核结果
├─ results/compliance/    招标要求合规检查结果
└─ results/report/        最终审核报告 Markdown/HTML
```

路径规则不可跳过：

1. 相对 `--output` 必须以 `{SKILL_DIR}` 为基准解析，不能以命令调用时的当前目录为基准；
2. 显式绝对输出路径必须位于 `{SKILL_DIR}` 内；
3. 禁止 `..`、符号链接或其他路径穿越把生成物写到 `{SKILL_DIR}` 外；
4. 在创建目录或写文件前校验规范化路径边界，越界立即停止并报告；
5. 输入文件可以位于 `{SKILL_DIR}` 外，但生成物不可以；
6. 项目名用于目录名时仅做操作系统安全字符处理，不改变报告中的原始项目名。

## 标准流程

### 1. 建立资料清单

记录每个输入的绝对路径、类型、所属范围（招标/技术标/商务标/规则）、读取状态和警告。区分原始文件与解析产物，保留原始文件不覆盖。确认项目目录和五个输出目录均位于允许边界内。

检查点：输入完整、项目名明确、输出路径通过边界校验。

### 2. 逐文件解析

对招标文件、技术标、商务标逐个调用 `bes-document-parsing`，输出到 `{项目目录}/parsing/` 下相互隔离的子目录。必须等待每个文件完成并检查其 Markdown/manifest：

- 保留文件相对路径、章节标题、Markdown 行号，以及能获取的页码/表格/工作表位置；
- 检查扫描页、嵌入图片、OCR、表格断裂、乱码、空文件和重复内容；
- `partial` 或 `failed` 必须传递到后续审核并写入限制，不得声称完整解析；
- 解析失败的文件仍列入资料清单，并说明受影响的审核范围。

检查点：每个输入都有可追踪解析状态和输出路径；存在关键解析缺陷时，结论至少为“需要人工复核”。

### 3. 提取业务审核规则

调用 `bes-bid-rule`，规则来源优先级为：用户明确规则内容 > 用户指定规则文件 > 子技能默认规则。输出到 `{项目目录}/rules/`。保留规则原文及其模块、审核项、审核要点、风险等级、规则类型、关联模板和规则描述；不得在提取阶段判定合格或不合格。

若规则为空、格式无法读取或不同来源冲突，记录输入问题并停止业务规则审核；合规检查是否继续，须依据招标文件解析结果单独判断。

检查点：规则数量可统计，每条规则有唯一索引或原始行号，规则来源已记录。

### 4. 逐条业务规则审核

遍历每条规则，调用 `bes-bid-rule-review`，输入该条规则和技术标/商务标解析目录，输出到 `{项目目录}/results/check/`。文件名使用稳定索引，例如 `RULE-001.json`，不得使用会覆盖其他结果的非唯一名称。

必须遵循子技能的证据循环：模板线索 → 规则名称/审核项 → 规则关键词；对每个必要条件分别核对；继续检索直到证据充分、候选范围耗尽或出现无法解决的解析/证据冲突。

结论只允许：`符合`、`不符合`、`无法判断`。每个 `不符合` 或 `无法判断` 必须包含已核实事实、证据位置、缺失信息和对应改进建议。未找到证据不等于已证明不符合。

检查点：每个规则都有结果文件；结果是单个合法 JSON；规则字段与原规则一致；证据位置可回溯到解析文档。

### 5. 招标要求合规检查

调用 `bes-bid-compliance-check`，输入招标解析目录和投标解析目录，输出到 `{项目目录}/results/compliance/`。先从招标文件建立要求清单，再逐条核对投标证据，至少覆盖：资格、废标/符合性、评分、格式封装、递交时间及其他明确要求。

状态只允许：`通过`、`不通过`、`缺失`、`存疑`、`不适用`、`未核实`。只有招标文件明确规定无效/废标等后果时，才将风险标为致命；评分项只评估响应证据和可获得分值，不虚构评委最终得分。纸质签章、密封、银行到账、实物数量和电子介质等没有现场或凭证证据时必须为`未核实`。

输出必须是该子技能规定的单一合法 JSON，并由逐项结果实际计算统计数字。若任一必需解析目录不存在、为空或没有可用 Markdown，输出“输入错误”。

检查点：每条要求有招标出处；每个高风险结论有投标证据或明确缺失说明；统计与明细一致。

### 6. 汇总并生成报告

仅在前述结果文件可读取时调用 `bes-bid-report`，输入业务审核结果、合规检查结果及必要的解析警告，输出到 `{项目目录}/results/report/`。报告只能整理已有结果，不补写法规、事实、评分或结论；冲突和未核实事项必须单列。

报告至少包含：项目与输入、总体结论、致命/重要问题、逐项证据、风险与整改建议、待确认事项、解析限制和结果文件索引。调用 `bes-md2html` 将本次 Markdown 报告转换为同目录 HTML，并验证两者均存在且非空。

## 总体结论规则

汇总时按以下优先级，不得用平均分掩盖致命项：

- `输入错误`：必需输入或必需解析结果不可用；
- `不合规`：存在明确不通过/缺失的致命招标要求，或业务规则明确判定不符合且其风险为致命；
- `需要人工复核`：没有已确认致命不合规，但存在致命/重要存疑、未核实、解析异常或证据冲突；
- `合规`：所有适用高风险要求通过或明确不适用，且无未解决限制。

若业务规则结果与合规检查结果方向不同，分别保留两种结论，报告中说明判定来源，不擅自合并为单一结论。

## 失败与恢复

- 任一阶段失败：保留已经成功生成的产物，记录失败阶段、输入、错误和影响范围；
- 子技能不可用：停止依赖该子技能的阶段，不伪造替代结果；仍可执行且不依赖它的阶段需明确标注为局部结果；
- 输出路径越界、写入失败或文件被覆盖风险：立即停止写入并报告，不尝试换到技能目录外；
- 部分结果不得包装成“审核完成”或“全部合规”。

## 最终交付检查

完成前逐项确认：

1. 输入清单、解析状态和警告已保存；
2. 规则结果数量与规则数量一致，文件名唯一；
3. 合规结果与明细统计一致；
4. 报告 Markdown 和 HTML 均可读取、非空、位于 `results/report/`；
5. 所有结论均能追溯到招标原文、投标证据或明确的缺失/限制；
6. 明确列出阻断项、人工复核项、未完成阶段和用户需要补充的材料。

最终回复应简要列出：项目名、总体结论、已生成的主要文件路径、致命/重要风险数量、未核实事项、失败或限制。路径使用绝对路径或可点击本地文件链接，不声称未验证的产物已生成。
