# 投标文件合规检查

## 任务边界

只检查用户指定目录中的已解析 Markdown 文档，不自行读取未授权目录，不把通用经验当作本项目要求。招标文件是本次检查的唯一规则来源；“常见风险”只能作为额外提醒，不能据此判定不合规。

必需输入：

- `tender_dir`：招标文件 Markdown 根目录；
- `bid_dir`：投标文件 Markdown 根目录。

可选输入：项目名称、投标截止时间、是否执行递交前实物检查、额外文件范围说明。若用户只给出一个目录或目录不存在，先在 JSON 中报告输入错误；不要假设另一个目录的位置。

## 文件读取与证据定位

1. 递归枚举两个目录下的 `.md`/`.markdown` 文件，按相对路径排序；忽略隐藏文件和无法读取的文件，但将无法读取项记录为输入警告。
2. 阅读每个文件的完整内容，保留文件相对路径、标题层级、表格行、列表项和 Markdown 行号。不得只依赖文件名或目录名推断内容。
3. 招标文件证据位置使用：`相对路径#章节标题:L起始-L结束`；投标文件证据位置使用同样格式。没有可靠行号时使用 `相对路径#章节标题`，不得伪造页码。
4. 识别解析异常（乱码、缺页、表格断裂、OCR 不完整、空文件、重复内容）。异常可能影响结论时，对相关检查项判为 `suspect`，并在警告中说明。
5. 先建立招标要求清单，再核对投标文件。不得用投标文件中的承诺反向修改招标要求。

## 提取招标要求

逐章提取每一条可验证要求，包含原文、出处、适用条件、约束值和后果。重点检索但不限于：

- 资格：主体资格、资质/许可证、财务、纳税和社保、业绩、人员、信用、联合体、分包；
- 废标/符合性：保证金、投标有效期、报价上下限、核心技术/商务偏离、签字盖章、授权、响应格式、份数、装订、密封；
- 评分：评分维度、满分、分值、评分条件、证明材料、扣分规则；
- 递交与时间：截止时间、地点、澄清/答疑、踏勘、开标、现场出席、电子介质；
- 其他：语言、替代方案、国产/进口限制、合同实质性条款、递交前特别声明。

每条要求生成唯一“要求编号”，并标记：

- “要求类别”：`资格审查`、`废标/符合性`、`评分`、`格式与封装`、`递交与时间`、`其他`；
- “风险等级”：`致命`（违反可能导致无效/废标）、`重要`、`扣分`、`提示`；
- “适用性”：`适用`、`有条件适用`、`未知`；
- “适用条件”：触发条件；若无法确认，写明 `未知`，不要擅自判定适用或不适用。

明确区分“资格审查不通过”“废标/无效投标”“评分扣分”“格式整改”。只有招标文件明确规定，或明确写出“无效/废标/不得通过”等后果时，才标记为 `fatal`；模糊或通常性要求不得升级为废标项。

## 逐项核对规则

对每一条适用或可能适用的要求，在投标目录中寻找直接证据，并保留最相关的一个或多个位置。状态只能是：

- `通过`：证据明确存在，且与要求的数值、名称、日期、版本、签章/格式等约束一致；
- `不通过`：找到明确证据表明不满足；
- `缺失`：要求适用，但未找到必要响应或证明材料；
- `存疑`：存在相关内容，但值不一致、证据不完整、解析异常或无法可靠判断；
- `不适用`：仅在投标文件或招标文件明确证明该条件不适用时使用，并记录依据；
- `未核实`：仅用于不要求投标文件响应、且无法从现有材料验证的客观事项（例如实物密封、保证金实际到账）。不得用它掩盖缺失证据。

判定纪律：

- 缺少关键证明材料不得因“可能在附件中”判为通过；
- 数字、日期、金额、份数、有效期、比例必须逐字或可计算核对；计算过程写入“分析说明”；
- “满足/完全响应”声明不能替代招标文件要求的证明材料，除非招标文件明确允许声明替代；
- 关键要求没有足够证据时判 `suspect`，并给出人工确认动作；
- 每个 `fail`、`missing`、`suspect` 必须有具体补救建议；
- 对投标文件中发现但招标文件未要求的内容，不判为合规加分，也不作为违规，必要时放入“其他观察”；
- 不得声称已核验纸质签章、实物密封、银行到账、电子介质可读性，除非输入中有相应可验证证据。

对评分项只评估“响应完整度/可获得分值的证据”，不虚构评委最终得分。若评分细则不足以计算得分，“预计得分”使用 `null`，并说明原因。

## 递交前检查

只有用户明确要求递交前最终检查时，增加以下检查项：保证金实际到账、纸质正副本数量、逐页签章/骑缝章、密封和外包装标识、电子介质可读性、报价复核、递交地点和时间。没有现场或凭证证据时状态使用“未核实”，不要当作通过或失败。

## 固定 JSON 输出契约

最终只输出一个合法 JSON 对象，不要输出 Markdown 表格、代码围栏、解释性前后缀或尾随逗号。所有字符串使用 JSON 转义；未知文本使用 `null`，空数组使用 `[]`。日期优先使用 ISO 8601；原文日期无法标准化时保留原文并在“分析说明”中说明。

## 汇总判定

- `输入错误`：任一必需目录不存在、为空、无法读取，或没有可用 Markdown 文档；
- `不合规`：至少一条适用的 `致命` 要求为 `不通过` 或 `缺失`；
- `需要人工复核`：没有已确认致命不合规，但存在任一 `致命`/`重要` 要求为 `存疑` 或 `未核实`；
- `合规`：所有适用要求均为 `通过` 或明确 `不适用`，且不存在上述未核实的高风险项。

“检查概况”的数量必须由“逐项检查结果”实际计算，不得手填。“未关闭致命项数量”统计适用且状态为“不通过”“缺失”“存疑”或“未核实”的致命要求。“风险与行动清单”只收录需要行动的项目，并引用对应“要求编号”。

## 质量门槛

- 必须覆盖招标 Markdown 中所有可验证要求；若可能漏读，写入“检查局限”，不能输出“全部合规”；
- 每条要求必须有招标出处；除明确不适用外，每条核对结果必须有投标出处或说明未找到；
- 不能把通用经验、模型常识或“应该没问题”作为证据；
- 不能合并会导致不同后果的要求；金额、日期、份数、证书、人员和签章等应拆成可独立判定的项目；
- 输出必须是可被 JSON 解析器直接解析的单一对象。
